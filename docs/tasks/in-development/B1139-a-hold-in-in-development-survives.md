# B1139 — A hold in in-development survives the session that took it, and nothing says the work already merged

## Why

On 2026-09-09 `in-development/` held fourteen tickets. Six were live. **Eight
were not, in four different ways**, and telling them apart took an hour of git
archaeology that `npm run tasks` could have done in a second:

- **B1014, B1015** already carried a `superseded:` field in their own
  frontmatter and were sitting in `in-development/` anyway. The lane and the
  frontmatter disagreed and nothing said so.
- **B1098, B984** had their work merged to `main` (`93fe9bba`, `81d02ba3`) and
  never moved. B984 was 25h stale and three later tickets — B784, B1009, B1033 —
  had already been closed *against* it.
- **B1035, B1039, B879** each had a branch with committed work, a clean
  worktree, and no session alive. B879's was two days old and 927 commits
  behind `main`.
- **B108** had no branch, no worktree and no commit at all: a three-day hold on
  work that had never started, and which was blocked behind B102 and B103 by its
  own forced order anyway.

`scripts/tasks.mjs` already has every input it needs. `heldFor(claimed)` prints
the age (`scripts/tasks.mjs:219`), and that age is the *only* signal — a 3-day
hold and a 3-minute one differ by a string in a table nobody diffs.
`refuseIfHeld` (`:312`) then refuses the ticket to the next agent and says
*"If that session is gone, take it with --force"* — which is exactly the
question the tool declines to answer.

The cost is not just the archaeology. A stale hold is **invisible work**: the
next session asking for something to pick up is told these fourteen are taken,
so four merge-ready branches sat unmerged for up to two days while the backlog
was described as having nothing free.

## Work

Give the lane table one derived column, computed rather than stored — the same
principle as the status coming from the folder.

- **The frontmatter contradicts the lane.** A ticket carrying `superseded:` or
  `wontDo:` anywhere but `backlog/` is a filing error. `npm run tasks -- tidy`
  already re-files within a lane; this is the case it does not cover.
- **The work is already on `main`.** For a ticket in `in-development/`, ask
  whether a branch matching its id is an ancestor of `main`, or whether a commit
  naming the id is. Report as *merged, not moved*.
- **The branch is done and unmerged.** A branch matching the id exists, its
  worktree is clean, and it has commits `main` does not. Report as *ready to
  merge*, with how far behind `main` it is — the number that decides whether it
  is a merge or a rescue.
- **The holder is gone.** Nothing here can prove a session is dead, and it must
  not guess. But `claimed:` older than some plain threshold, with no worktree
  and no branch, is worth saying out loud rather than printing as an age.

Not doing: moving anything automatically. Every case above is a report, and the
lane move stays a decision — `completed/` and `open/` are a person's lanes and
this must not become a way around that. Also not doing: killing or unclaiming
another session's hold. `--force` already exists and is the right escape hatch;
this only tells the person whether to use it.

## Acceptance

Reproduce the 2026-09-09 state on a scratch branch — a ticket in
`in-development/` carrying `superseded:`, one whose branch is an ancestor of
`main`, one with a clean unmerged branch, and one with no branch at all — and
`npm run tasks` names all four without any git command being typed by hand.
A live ticket with a dirty worktree and a fresh `claimed:` is not flagged, which
is the case that must not produce noise. `npm run verify` green.

## Built, 2026-09-11

Console output only (`npm run tasks -- list`, i.e. plain `npm run tasks`) —
not INDEX.md. That table is committed and regenerated by every session; a
computed "merged Xh ago" string baked into it would churn on every regen for
no reason connected to the task itself, which is its own kind of noise. A new
`holdNotes(item)`, called from `list()`'s per-item line, covers all four cases
for a ticket in `in-development/`:

1. **Frontmatter contradicts the lane.** `superseded:` or `wontDo:` set while
   still in `in-development/` prints so directly.
2. **The work is already on `main`.** `latestMergeEvidence(id)` walks
   `git log <trunk>` for the most recent commit whose subject matches
   `\bID\b` *and* `merged, awaiting review` — the exact phrase this
   repository's own sessions already write when `move` takes a ticket to
   `testing/`. That is deliberately narrower than "any commit naming the id":
   a capture, a wave-take and a park all name the id too, on trunk, because
   task files commit straight there, and matching any of those would flag a
   ticket the moment it is captured.
3. **A branch matching the id has unmerged work.** `branchWork(id)` looks for
   a local branch named `b<number>-*` (the `work-on-a-task` convention) with
   commits `trunk` does not and a clean worktree, and reports it as ready to
   merge with how far behind. A branch whose tip **is** the merge-base — no
   commits yet — is not a signal and is skipped, which is what keeps a
   ticket claimed moments ago and not yet built quiet.
4. **The holder is gone.** No merge evidence, no branch, and `claimed:` at
   least 24h old.

**The park-vs-stale distinction (the part that matters):** case 2 compares
`latestMergeEvidence(id).at` against the ticket's own `claimed:` — the exact
timestamp `move()` already writes every time a ticket *arrives* in
`in-development/`, including a deliberate park back into it. A ticket
retaken *after* its code merged carries a `claimed` newer than the merge and
prints nothing; only a hold that has sat untouched **since before** its code
landed — merged and genuinely forgotten — is reported. No new field, no
prose heading to parse: the frontmatter field a person already writes and can
correct is the marker.

**The free rehearsal.** Ran the built script (`npm run tasks`, read-only —
no `move`) against the live tree on 2026-09-11 ~17:00 UTC. `in-development/`
held ten tickets; three were the cases named in the Why section, plus one
genuinely live branch:

- **B1272** (session's own, claimed 4h ago, carries `## Parked back here`):
  silent. Its code merged at 05:34 UTC via a "B1272: merged, awaiting
  review" commit; `claimed` (11:12 UTC) is well after — retaken post-merge.
- **B1394** (claimed 4h ago, carries `## Back to in-development`): silent.
  Merge evidence at 09:55 UTC ("B1280, B1393, …, B1394, B1396: merged,
  awaiting review"); `claimed` (10:53 UTC) is after it by about an hour.
- **B1384** (claimed 10h ago, no such heading — a large ongoing DOCS
  ticket, never fully moved to `testing/`): silent, and for a different,
  simpler reason than the other two — it has *no* commit anywhere on trunk
  matching "B1384 … merged, awaiting review" at all (its commits are all
  "B1384 (README.md area)" and similar partial-area messages), so case 2
  never fires for it in the first place. No heading-parsing was needed to
  keep this one quiet.
- **B1112** (a sibling worktree, unrelated to this ticket): flagged —
  `branch b1112-plan-prose has 2 commits main does not, 7 behind main —
  ready to merge`. Confirmed by hand (`git log --oneline main..HEAD` in
  that worktree: 2 real commits, clean tree) — a true positive for case 3,
  not a false one.
- The other six (this session's own fresh takes, `claimed` ~10 min old):
  silent, as required by the acceptance line about a fresh hold not
  producing noise.

So on the live tree, right now, the mechanism is 3-for-3 on staying quiet for
the deliberate holds and correctly informative on the one ticket with real
unmerged work sitting nearby. `npm run verify`: 525 files / 6901 passed, 4
skipped, `npm run unused` clean.
