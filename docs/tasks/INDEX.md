# Fernscout — tasks

`docs/plans/` is work that was planned and then built. This directory is the
live list: features to add and problems found in the code, from the moment
somebody thinks of one to the moment it ships.

**The folder is the status.** A task is a file that moves:

```
docs/tasks/
  backlog/           captured, not yet reviewed — anyone may add here
  open/              reviewed and approved; an agent may pick these up
  in-development/    somebody is on it now
  testing/           merged, waiting for a person to try it
  completed/         verified by a person, kept as the record
```

**Two of those lanes are gates, and a person holds both.**

`open/` is the way in. An agent asked to find itself something useful takes
work from `open/` and nowhere else; anything it notices along the way it
writes into `backlog/`. Promoting `backlog/ → open/` is the author's decision,
and it is what keeps "here is a list of things you could do" from becoming "an
agent decided what this project needs next".

`completed/` is the way out. An agent takes a task as far as `testing/` —
merged, verified against its own acceptance criteria — and then says what to
look at. A task is done when somebody has seen it working, not when its tests
pass.

The three lanes in between are ordinary bookkeeping and an agent moves through
them on its own. `.claude/skills/work-on-a-task/` is the build loop;
`.claude/skills/manage-tasks/` is the bookkeeping around it.

There is no `status:` field in the frontmatter. A status kept in two places
disagrees with itself within a month — the same reason the entry and trip
field lists live in one skill each rather than in `AGENTS.md` too.

The tables below are generated by `npm run tasks` from the files on disk.
Do not edit them by hand; run the script.

## Frontmatter

```yaml
---
id: B01                 # assigned by the script
title: one line — the problem, not the fix
type: SECURITY          # SECURITY · ISSUE · FEATURE · CHORE
priority: high          # high · medium · low — cost of leaving it alone
complexity: low         # low · medium · high — cost of fixing it
area: rate-limiting     # comma-separated, free-form
found: "2026-09-01"
started: "…"            # added by `move … in-development`
completed: "…"          # added by `move … completed`
---
```

`priority` and `complexity` are independent, and B01 is why both exist: a
one-line fix for the most serious thing on the list.

Cross-reference other tasks **by id in prose** (`see B01`), never by relative
path. Files move between lanes, and a path link breaks the moment one does.

## Where the security tasks came from

A read of the security-relevant surfaces on 2026-09-01: auth and sessions,
trip and draft access, media serving and upload, the outbound fetch, and the
deployment's headers. It was a review by reading, not a pentest, and nothing
there was proven by exploit except B01, which is plain from the code and the
proxy's documented behaviour.

Not everything looked at became a task. What held up: two-layer path traversal
defence in `resolveMediaFile`, tokens hashed and compared with
`timingSafeEqual`, OTP failures collapsed to one indistinguishable answer,
cookies `httpOnly` + `sameSite: lax` + `secure` in production, contacts under
AES-256-GCM with the key in the environment only, parameterised queries
throughout, the media gate running before file resolution and refusing with
404, an unrecognised `visibility` reading as `private`, and drafts filtered in
one place rather than at each call site.
