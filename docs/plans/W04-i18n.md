# W04 — Two language layers + locale URLs

**Roadmap:** A3, M7, decision 13 · **Depends on:** W02 · **Wave D**

## Goal
UI chrome is translated by us in a maintained set; content is written in any
language at all. Every language has its own URL.

## Scope

### Two layers (ROADMAP §1.2)
| | UI / chrome | Content |
| --- | --- | --- |
| Provided by | us: `de`, `en`, `hu` | the author, any language |
| Missing → | **English chrome** | entry's default text |

- Move the `DICT` in `lib/i18n.ts` to `content/locales/<code>.json`, shipping
  `de`/`en`/`hu` as maintained defaults that a self-hoster can override or extend.
- `LOCALES` / `LOCALE_LABEL` become the *maintained dictionary set*; the active
  list comes from `config.site.locales`.
- **`parseTranslations()` in `lib/trips.ts` hardcodes `["de","hu"]`** — must read
  the configured list. Same for entry frontmatter parsing in `lib/entries.ts`.
- **`defaultLocale` is `de`**, not English (decision 13).

### Locale URLs (M7)
- `/[locale]/…` routes with `hreflang` alternates and a canonical.
- `/` redirects to `defaultLocale` (or negotiates on `Accept-Language`).
- Sitemap emits every locale; OG images pick up the right language.
- Locale switcher preserves the current path.

## Status — Part A done, Part B open

**Done: the two language layers.** Dictionaries live in
`content/locales/<code>.json`, are read on the server and handed to
`LocaleProvider` as props. `installedLocales()` is the maintained set; a
journal's own languages come from its config, and one we ship no chrome for
gets English chrome around its own content. Translation types are open by
locale code rather than a `de | hu` union, and `parseTranslations` reads
whatever the file offers.

The server now renders **the journal's own language**. Before, it rendered
English and swapped after hydration, which is why search engines only ever saw
English. A reader's choice is a cookie the server reads, validated against
what that journal offers.

**Done differently: `?lang=` instead of `/[locale]/…`.** A language now has a
shareable address — `/severin/day/hoi-an?lang=hu` — without a second route
restructure. `middleware.ts` turns the parameter into the cookie the server
already reads, on the *same* request as well as the next, so the first click on
a shared link is already in the right language.

The sitemap emits `hreflang` alternates (plus `x-default`) for every page in
every language the journal offers, which is how a crawler learns these are
translations rather than duplicates.

**What this trades away, honestly.** A path segment is a stronger signal to
search engines than a query parameter, and it caches better at a CDN, where a
page varying by cookie does not. For a journal read by a few dozen people who
arrive from a link somebody sent them, that is the right trade; for a site
competing on search it would not be. Revisit if the hosted product (§12)
happens.

Still open: the root layout owns `<html>` and cannot know whose journal is
being read, so it renders the instance's language and
`components/HtmlLang.tsx` corrects the attribute after hydration for a journal
in a different language. A locale segment would remove that correction.

## Acceptance
- [ ] `/de/…`, `/en/…`, `/hu/…` all resolve and are linkable
- [ ] A locale with no dictionary renders **English chrome + its own content**
- [ ] Adding a locale to config with a new `content/locales/xx.json` needs no code change
- [ ] `hreflang` + canonical correct on every page; sitemap covers all locales
- [ ] Existing `#day-<slug>` fragments and `/day/<slug>` permalinks still work
