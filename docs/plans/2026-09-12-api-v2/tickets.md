## 2. Backlog finds, grouped by classification

### 1 — Absorb into v2 now

- **B678 — the helper re-implements the file-shape rules (validation duplication).** Proposes `POST /api/v1/<user>/validate` — a dry-run endpoint answering "what's wrong with this document" without writing, using the same validators the write routes use. This is directly a v2 primitive: since v2 makes 422 bodies list every missing/declinable field with why_required and a schema excerpt (rule 2), a dedicated validate door (or the same semantics surfaced via a `dryRun` flag on the write) would let the helper/BYOA agents check a document before committing bytes, and eliminates the two-implementations-disagree failure this ticket documents. Design a validate capability into each v2 resource now, not as an afterthought.
- **B1503 — a media file belonging to no day cannot be written through any door.** v1's media route requires an existing `day` and does two things at once (store bytes + splice into gallery). This blocks a trip `cover` being set before its day exists and blocks restoring an orphaned file. v2's media resource (the single binary door: photo | bank_export | gps_history | document) should explicitly support a day-less trip-scoped photo write and a day-less delete, with attach-to-day as a separate operation — this is the same underlying shape as B1525's cover-ordering problem above; solve both with one design.
- **B1069 — no tool surface for a "guided" agent (BYOA).** Already decided by the owner: do the documentation pass first (B311, done), and MCP/tool-surface work should be "a thin delegation with no logic of its own" if it returns at all — every tool = one documented route+verb, no second vocabulary. This is precisely v2's stated principle (contract layer new, domain layer shared, schema-generated docs). Treat this ticket's decision as a design constraint on any future v2 tool-surface layer: it must be generated from the v2 schemas, never hand-maintained.
- **B1589 (in-dev)** — see table above; fold `intro` into the trip translations sub-schema now.
- **B1529 (testing)** — see table above; media ceilings surfaced pre-upload, and echo what was actually stored.
- **B1564 (in-dev)** — see table above; declined-field retraction must be a schema-level invariant, not a per-route habit.

### 2 — Collision (in-flight work v2 will rewrite)

- **B1567 (in-dev)** — start_day double-press / idempotent create; fix the v1 route now, but the "second create → 409 with stored document" behaviour is v2's actual answer (rule 6). Note this in the quirk ledger rather than re-deriving it.
- **B1585 + B1591 (testing)** — owner-tool visibility UI built against today's PATCH routes; flag for a v2-compatibility check once trip/day/journal write shapes settle, since these are cookie-only `/api/web`-shaped routes sitting right next to what v2 is redesigning.
- **B1577 (testing)** — the `doors` mechanism (content-model.json) is itself v1-era plumbing being actively built; it should be understood as temporary scaffolding that v2's document-oriented contract retires, not as a pattern to imitate in v2.

### 3 — Solved by v2 (candidate for superseded-by-v2 once v2 lands)

- **B1520 (testing)** — slug-collision-at-publish: eliminated by client-chosen ids (rule 6).
- **B1525 (testing)** — "eight trip fields have no door", hand-kept key lists drifting: eliminated by whole-document PATCH + schema-generated contract.
- **B1577 (testing)** — doors section itself becomes unnecessary once helper is rewired onto v2 (per B1587's own migration order: schemas → parallel v2 → helper rewired → webapp → v1 sunset).
- **B1584 / B1586 (backlog issue)** — `captions`/`photoVisibility` accepted by the API but absent from `content-model.json`, and a browser-side allow-list (`EDITABLE` in the day-edit route) separately rejecting the same fields and taking the rest of a save down with it. Both are symptoms of the same disease as B1577/B1525: multiple hand-kept field lists (API validator, content model, browser route allow-list) that can silently diverge. v2's "one field, write and read" rule (4) plus a single generated schema per resource removes the class of bug, not just these two instances.
- **B1028 (backlog small-feature)** — owner's own trip form (`/api/trip`, `DETAILS` list) can't edit fields the agent-facing API (`patchTripDetails`) already accepts, because the two keep separate field lists sharing one function underneath. v2's stated rule ("contract layer new, domain layer shared") is the direct fix: one trip schema, one set of writable fields, shared by the owner's browser door (`/api/web`) and the agent door (`/api/v2`).
- **B1384 / B1547 (backlog docs-and-skills)** — documentation.txt / skill docs drift from the live API and read as machine-generated prose maintained by hand. v2's schema-generated documentation (replacing skillDocs markers, per B1587's summary) directly targets this; these tickets' problem disappears once v2's generated docs ship, though the *editorial voice* concern in B1547 (a person must still read the rendered prose for tone) survives generation and should be scoped as a follow-up even after v2 lands.

## 3. Design changes v2 should make now, because of these tickets

1. **A validate/dry-run capability per resource** (from B678). The 422-with-full-problem-list behaviour v2 already mandates for silent omission should be reachable *without* committing a write — either a `dryRun` flag on the write door or a dedicated validate call sharing the same schema. This is what kills the helper's remaining hand-rolled duplicate validators (B678) and removes the two-implementations-disagree failure class outright.
2. **Trip-scoped, day-less media writes and deletes** (from B1503, and B1525's `cover`-ordering problem). The media resource must support: store bytes against a trip with no day yet, delete a file no gallery references, and only *then* let `cover` reference it. Document the ordering constraint (`cover` must name a `src` the gallery already holds) as a conditional field (rule 3) rather than leaving it an undocumented sequencing trap.
3. **Idempotent, id-scoped day/trip creates** (from B1567, B1520). Client-chosen ids (rule 6) already covers this in principle; make sure the day-create door specifically answers a second create for the same id with 409 + the stored document, not a second success — this was the exact bug B1567 found in v1's helper-facing create route.
4. **Trip translations schema covers `intro`, not just `title`/`tagline`** (from B1589). Build the full set now so photobook/postcard text-resolution code has one place to read from, rather than the field-by-field growth that already happened three times on the trip PATCH surface (title/tagline/start/end, then cover, then accent/costsVisibility/intro — see B1525's history).
5. **One writable-fields list per resource, shared by `/api/web` and `/api/v2`** (from B1028, B1584/B1586, B1577, B1525). Every instance of "the browser door and the agent door keep separate field lists that drifted" (four found in one week of tickets) is the same bug. v2's "contract layer new, domain layer shared" principle must extend to the owner-facing `/api/web` routes too, not only the bearer-token `/api/v2` surface — otherwise this class of bug reappears one door over.
6. **Migration ledger note: retire `content-model.json`'s `doors` section and the helper's fallback key lists** once helper is rewired onto v2 (B1577's whole apparatus becomes dead weight — say so explicitly rather than leaving it as permanent infrastructure).
