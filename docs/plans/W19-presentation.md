# W19 — Presentation mode, slideshow, route video

**Roadmap:** I1–I5 · **Depends on:** nothing · **Wave E**

## Goal
"Show us the trip" takes eight minutes, not three hours, and looks good on a TV
over AirPlay.

## Scope
- **I1 Presentation mode**: 16:9 landscape, big type, no chrome, keyboard/remote
  control, auto-advance with per-slide dwell, works over AirPlay/Chromecast
  mirroring. `components/SlideShow.tsx` is the seed.
- **I2 Narrated cut**: one slide per day — best photo + one sentence, generated.
- **I4 Wake lock** so the screen doesn't sleep mid-show.
- **I5 TV-legible type** — the same work that helps older readers (W17/J2).
- **I3 Route video/GIF** export of the journey unfolding. This is the most-shared
  artefact in the category (FindPenguins gives it away free). Heavier; may slip.

## Status: I1, I2, I4, I5 done. I3 left for later (see below).

`components/SlideShow.tsx` now drives two "cuts" behind one presentation
surface, switchable while it's running:

- **Highlights** (I2, the new default) — one slide per calendar day: the
  day's best photo plus one real sentence pulled from the entry's own prose.
  Generated by `lib/narratedCut.ts` (`buildNarratedCut`, unit-tested in
  `test/narratedCut.test.ts`), from the same `places[].entries` the page
  already passes in — no new data-fetching, no new route.
  - **Best-photo heuristic** (documented in the module): an entry's own
    `cover` wins outright, since it's already hand-picked; otherwise the
    largest landscape-orientation photo across the day (landscape fills a
    16:9 frame; a portrait phone shot letterboxes to a sliver); otherwise the
    largest photo of any orientation; without width/height metadata every
    candidate ties and it falls back to the first photo of the day. A
    video-only or photo-less day gets `undefined` and renders a text-only
    card — the "no photos at all" case is a normal path, not an edge case.
  - The one sentence is `firstSentence()` on the entry's (localised) content,
    markdown stripped. Nothing is invented — an entry with no prose falls
    back to showing just its title.
- **Full tour** (the original seed) — every stop and every photo/video, map
  flythrough included, kept for anyone who wants the long version.

Shared infra (I1/I4/I5), on both cuts: a 16:9 letterboxed frame (`min(100vw,
100vh·16/9)`, falling back to filling the screen on a portrait phone, which
this never targets but shouldn't visibly break on either); chrome that
fades out during playback and returns on any key/pointer activity;
arrow-keys/PageUp/PageDown/space/Escape (covers the common presenter-remote
key mappings); a +/- control for per-slide dwell (3-15s, default 6s); a
`navigator.wakeLock` hook (`components/useWakeLock.ts`) that no-ops where
unsupported; a manual full-screen toggle (`requestFullscreen`, always
user-gesture-triggered rather than auto-fired, since browsers — Safari
especially — don't reliably honour an un-gestured request); type sized with
`clamp(...vw...)` so it scales with the actual mirrored screen. Both
`GalleryPageContent` and `MapPageContent` load it via `next/dynamic({ssr:
false})`, per `PERF-1` — nobody pays for the map-projection/motion bundle
until they press "Slideshow".

Trip visibility is inherited for free: presentation mode isn't a new route,
just a mode of the existing overlay on `/gallery` and `/map`, both already
behind `mayReadTrip` in `app/(current)/layout.tsx` / `app/trips/[trip]/layout.tsx`.

### I3 — route video/GIF export (not built)

Left out, as scoped. What it would actually take, for whoever picks it up:

- A server-side render path — canvas/WebGL frame capture (e.g. the existing
  `SlideMap` SVG re-driven headlessly, or re-implemented in canvas) piped
  into `ffmpeg` for MP4/GIF encoding. None of that runs in a browser tab;
  it needs a server job (or a heavy client-side WASM ffmpeg build, which is
  multi-hundred-KB and slow enough to want a progress UI of its own).
- A queue/job model, since encoding a multi-minute route animation takes
  much longer than a request-response cycle — this wants the kind of
  background-job infra `W07`/`W11` already have reasons to build, not a
  bespoke one-off here.
- A decision on where rendered files live and how long they're kept
  (`content/<user>/...` per `W22`, presumably, with a cache-and-expire
  policy — these are not small files).
- GIF and MP4 want different encodes (palette-optimised GIF vs. H.264/H.265
  MP4); "route video/GIF" is really two output formats, not one.

None of this shares much code with the presentation mode built here beyond
`SlideMap`'s projection math — it is genuinely closer to a small render
pipeline than a UI feature, which is why it was heavier than the rest of
this package combined.
