Android location imports silently do nothing

Verified, not inferred

The file is accepted and produces zero positions

Google moved Timeline onto the phone in 2024. Android and iOS now write different files with different shapes — and the Android one passes our detector, then parses to nothing. No error, no warning. The person waits, sees an empty map, and concludes the feature is broken. It is.

// both shapes fed to importers/gps/google-timeline.ts
iOS/documented        detect=true  fixes=1
Android Timeline.json detect=true  fixes=0   ← accepted, imports nothing

Cause: parseGeoUri() in importers/gps/schema.ts:48 requires a geo: prefix. Android writes "35.0116°, 135.7681°". The object wrapper is fine — detect already matches semanticSegments and parse unwraps it, which is precisely why it gets far enough to fail quietly.

Other Android/iOS divergences the parser will meet next: placeId vs placeID, numbers as strings, and visit.placeLocation being a direct string rather than nested under latLng.

This blocks the Location flow. Writing beautiful step-by-step instructions that send half your users to a file the importer eats and discards makes the experience worse, not better. Fix the parser first; it is a separate, small, testable ticket.

The skeleton

Five steps, and only one of them changes anything

Every import type wears the same shape. NN/g's wizard rules apply exactly: this is unfamiliar, infrequent work, the steps must be visible, and the person must be able to leave and come back. Nothing is written until the last button — and that button is named after what it does, never "Continue".

The second door

WhatsApp as a file-transfer device

The file is on the phone. The screen is on the desk. That split is the whole reason both doors exist — and it needs almost no new plumbing, because inbound WhatsApp media already lands in content/<user>/inbox/ within seconds.

  • The link is wa.me/<number>?text=… — one tap on a phone, a QR code on desktop captioned "scan with the phone that has the file"
  • Always, in bold, under the button: attach with the paperclip → Document. Sent as a photo, the file is re-encoded and the location is thrown away. The dispatch code already documents this
  • The page watches — records openedAt, polls every 3s, first file arriving after that with a matching extension wins
  • After ~10 minutes it stops and says so, with the browser door as the fallback

One route to build: listInbox() exists in lib/inbox.ts, but only the bearer-token GET /api/v2/<user>/inbox exposes it. The cookie-side twin is roughly ten lines, and it is the only new plumbing either door needs.

No pairing code. Two simultaneous imports on one journal is not a real case, and a four-character code is a thing to type. Add one if inbox races actually show up.

The name

Call it import, and keep the warmth in the heading

CandidateDEHUVerdict
ImportImportImportálásTake it. The word every app they just came from uses — Photos, Contacts, their bank. Zero teaching cost, works as a noun in all three. Boring, which is the point
Bring inMitbringenBehozatalWarmest, matches the current heading — but has no usable noun in DE/HU. "Behozatal" reads as customs. Breaks exactly where it must not
CollectSammelnGyűjtésNice for photos, wrong for a bank statement. Implies Fernscout goes and fetches, which it does not
AddHinzufügenHozzáadásAlready means "add a day", "add a trip". Collides

The route and the nav label are the boring word. The heading is free to be a sentence, and should stay one: "What do you want to bring in?" · "Was möchtest du mitbringen?"

Before building

Costs, and what's still open

  • ~215 extract.* locale keys × 3 languages get renamed with the route. Budget for it, and run npm run i18n:keys after
  • B1803 is in development on these exact files right now. A rename would collide head-on. Sequence it, don't parallelise it
  • B1797 is already in testing and is literally "the import drops a person onto a bare file picker with no framing" — check its outcome before re-scoping this
  • Deleting the docs is a locale change too — docs.extract.title, extract.hub.guideHint and guideLink all go
  • Hungarian is not written. Every string in this concept has an EN and DE line; the HU lines are drafts nobody confident in the language has checked. The repo rule forbids shipping an invented translation
  • Google Photos Takeout sidecars — location lives in a *.supplemental-metadata.json next to a stripped image. Read it, or tell people to run exiftool? Reading it is kinder and not much code
  • Which banks after Revolut? Wise and N26 are the traveller defaults; CAMT.053 XML would cover most Swiss banks with one parser
  • Do the screenshots get maintained? Google moved this export once already. A screenshot that lies is worse than prose
