# Dark, light and automatic appearance

*Written 2026-09-13, before the work. Intent as it stood; not corrected
afterwards — `docs/plans/` is the record, not the documentation.*

This plan settles B1541. The appearance control lives on `/<user>/me` and has
three choices: **Automatic**, **Light** and **Dark**. It changes the whole site
in that browser, not the journal's published design for everybody else.

## Decisions

| Question | Decision |
| --- | --- |
| Whose preference is it? | The reader's, on this browser. It is not journal content and is never written to `config.json` or the database. |
| Where is it changed? | A visible Appearance section on `/<user>/me`, for owners, guests and signed-out readers alike. No session is required to choose how a public page looks. |
| What is the default? | Automatic. With no stored value, follow `prefers-color-scheme` and react when the operating-system choice changes. |
| How is it stored? | `localStorage`, under one site-wide key. Store only explicit `light` or `dark`; Automatic removes the key. Invalid or unavailable storage falls back to Automatic. |
| What does it cover? | Every browser-rendered page, including `/agent` and the branding benches. Generated print/PDF output and print-faithful previews stay light. |
| How is the palette built? | Keep the six named brand hue ramps as primitives. Add semantic screen roles for ground, surface, ink, rule, control and focus, then make those roles theme-aware. |
| What happens to the room-only switch? | Remove it and its `fs.agent.dark` state. The room follows the same global choice as every other page; its text-size setting remains room-specific. Do not promote an old room-only choice into a site-wide choice. |

There is no backend or API work in this feature. A theme preference is a
device display setting, not part of somebody's journal, export or backup.

## Why the existing tokens cannot just invert

The current utilities describe colours, not jobs. `text-navy-900` is strong
ink, while `bg-navy-900` is a strong control; `bg-white` is a card, while
`text-white` is ink on a dark button. Inverting one colour variable would make
one side of each pair right and the other wrong. The existing room-only dark
mode works around that with class-by-class overrides in `app/globals.css`, but
extending that exception list to the whole product would leave every new
component dependent on remembering a second stylesheet.

The current inventory is about 3,475 neutral/brand colour utility occurrences
across 151 files in `app/` and `components/`. This is a mechanical migration,
but it is not safe as an unreviewed search-and-replace because the property is
part of the meaning.

The light palette remains the source for primitive names such as `navy-900`,
`cream-50`, `yellow-400` and `green-500`. Screen UI moves to role names along
these lines:

| Existing use | Semantic role |
| --- | --- |
| page `bg-cream-50` | base ground |
| card or popover `bg-white` | raised surface |
| quiet `bg-cream-100` | inset/subtle surface |
| `text-navy-900` | strong ink |
| `text-navy-700` | body ink |
| `text-navy-600` / `text-navy-500` | secondary / muted ink |
| `border-navy-200` / `border-navy-300` | quiet / strong rule |
| dark `bg-navy-*` with light text | strong control plus on-strong ink |

Yellow remains the waymark and primary action. Green still means live or
ahead. Neither becomes decorative merely because the ground is dark. Focus
stays blue, and text on yellow stays `yellow-950` or the measured semantic
equivalent. Dark values are added to the identity bench so contrast is
computed, not copied into prose.

## Theme state and first paint

The document has three source states:

```
stored "light"  -> <html data-theme="light">
stored "dark"   -> <html data-theme="dark">
no valid value  -> <html> and prefers-color-scheme decides
```

The root layout includes the small inline bootstrap documented by this
checkout's Next.js guide, before content paints. It reads the validated stored
choice and adds or removes `data-theme` on `<html>` inside `try/catch`.
`suppressHydrationWarning` belongs on that element because the bootstrap may
change it before hydration. This keeps the root layout independent of cookies
and request data and avoids opting the whole app into dynamic rendering.

`viewport.colorScheme` becomes `"light dark"`. The two static
`theme-color` entries use light and dark media queries so browser chrome also
has an honest automatic fallback. When an explicit choice overrides the OS,
the client theme helper updates the matching theme-colour meta at the same time
as the root attribute.

CSS has explicit light and dark semantic values, plus an automatic dark media
block that applies only when `data-theme` is absent. Native controls inherit
the effective `color-scheme`. A `matchMedia` listener is needed only to keep
the selector's resolved-status hint and browser chrome current while Automatic
is selected; CSS itself handles the page without JavaScript after first paint.

## The control on `/me`

Add one small client component, separate from the already large
`MePageContent`, near the top of the page after the identity/sign-in summary.
It renders a labelled radio group rather than a binary switch, because three
states cannot be represented honestly by an on/off control:

- **Automatic** — follows this device
- **Light** — always use the light appearance
- **Dark** — always use the dark appearance

The chosen option applies immediately and is keyboard-operable. Automatic
also names the currently resolved result (light or dark) in quiet text, so a
person does not have to infer what their operating system requested. The
control uses the same 44px minimum target and visible focus treatment as the
rest of `/me`. Add native English and German copy and have the Hungarian copy
reviewed by a Hungarian speaker before merge.

It is shown to every `/me` reader. Requiring sign-in would make a purely local,
non-sensitive setting unavailable to the public readers who need it most, and
would falsely imply the choice is saved to their account.

## Order of work

1. **Theme contract.** Add a small pure `lib/theme.ts` contract for the key,
   allowed values and bootstrap source. Add the root bootstrap,
   `suppressHydrationWarning`, viewport metadata and tests for stored, absent,
   invalid and storage-refused cases.
2. **Semantic screen palette.** Add light/dark semantic role tokens to
   `app/globals.css`. Extend `lib/brand.ts` and `/docs/branding/identity` to
   present and measure both screen themes without changing the primitive brand
   palette.
3. **Preference UI.** Add `ThemePicker` to `/me`, translated in all maintained
   locales. It writes one site-wide preference, changes the document
   immediately and follows live OS changes in Automatic.
4. **Migrate the ordinary UI.** Replace neutral colour utilities in `app/` and
   `components/` by role, in reviewable groups: grounds/surfaces, ink, rules,
   controls, then shadows and translucent overlays. Leave stable brand accents
   primitive unless the contrast bench says a theme-specific role is needed.
5. **Handle exceptions deliberately.** Audit SVG/CSS drawings, maps, charts,
   photographs and overlays. Remove the room-only dark control and its scoped
   overrides. Pin print-faithful browser previews to light; do not touch the
   PDF/postcard/photobook renderers.
6. **Prove existing content.** Run the focused tests while migrating, then the
   full gate. Finally inspect real pre-existing pages and every branding bench
   at phone and desktop widths in Light, Dark and Automatic.

The migration should keep the app runnable after each group. Do not land a
half-state in which the root can select dark while major routes still carry
unmapped light surfaces.

## Automated checks

- Unit-test the preference parser and bootstrap for `light`, `dark`, absent,
  invalid and inaccessible storage.
- Component-test the `/me` radio group: selected state, keyboard labels,
  immediate root update, persistence, Automatic removal and OS-change response.
- Extend the undefined-colour-token check to semantic roles and both theme
  blocks.
- Extend the contrast checks so 11px text still clears AAA on every screen
  surface it uses, ordinary text clears its existing floor, and control/focus
  boundaries clear the non-text floor in both themes.
- Assert the root layout contains the pre-paint bootstrap and advertises
  `light dark` without reading cookies.
- Keep existing print renderer snapshots/fixtures byte- or pixel-equivalent as
  appropriate; a browser theme must not alter an order sent to a printer.
- Finish with `npm run verify`.

## Browser acceptance

Use a real browser, first at 390px and then at desktop width:

1. With no stored choice and emulated OS dark, open the landing page, an
   existing journal, trip and day. All paint dark on the first frame, with no
   cream flash.
2. From `/me`, select Light while OS dark; reload and navigate between the same
   routes. They stay light. Select Dark while OS light; reload and repeat. They
   stay dark.
3. Select Automatic, change the emulated OS scheme without reloading and check
   that the page, native controls, theme-colour metadata and resolved hint all
   follow.
4. Check `/agent`: it follows the global setting, the old independent dark
   switch is gone, and text-size S/M/L still works.
5. Inspect `/docs/branding/identity`, animation, travellers, day, order and
   print in both themes. (The repository now has five drawing benches plus the
   identity bench; B1541's older wording said four.) Print and print-faithful
   previews remain light.
6. Check focus rings, disabled controls, notices, popovers, dialogs, maps,
   charts, photo captions and the lightbox. At 390px,
   `document.documentElement.scrollWidth === clientWidth` remains true.
7. Check the browser console for hydration errors and capture the representative
   light/dark screenshots with the task handoff.

## Not in scope

- A journal owner choosing a palette for other readers.
- Syncing appearance between devices or accounts.
- A second toggle in the global header.
- Dark PDF, postcard or photobook output.
- Recolouring the Fernscout mark, inventing a seventh hue, or changing type and
  spacing as part of the theme migration.

No product decision remains open before implementation. The final dark values
are a visual review item in testing, constrained by the identity bench's
measured contrast and the existing brand roles.
