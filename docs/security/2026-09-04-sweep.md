# Security sweep — 2026-09-04

Task B22. A source review of `main` at `ff81d59`, run in the worktree
`g14-security-sweep`. Not a penetration test: nothing here was probed against a
running host. Attacking a deployed instance from outside is B101, and the last
section says which of these are worth taking there.

The trigger was that a morning of parallel agent work had landed on exactly the
code a sweep cares about, none of it reviewed by anybody but its author. Five
findings survived, four of them with a reproduction that runs in the test suite.
Two of the serious ones are in the *older* surface rather than in this morning's
work, which is worth saying: the new code held up better than the code it was
bolted onto.

## Findings

### 1. B230 — a code issued for one trip is verified into a journal-wide token

**High.** `app/api/auth/verify/route.ts:100-116`.

`/api/auth/request` refuses an agent code to anybody who is neither the
journal's owner nor on the trip they named. That check is right. But the trip is
never bound to the code — the `login_codes` row is keyed on
`(owner, email, kind)` — and the trip is re-supplied at redemption, where
`agentScope` returns `undefined` for every value it does not recognise:

```ts
if (!tripId) return undefined;
const trip = getTrip(tripRef(username, tripId));
if (!trip) return undefined;
return isOwnerAddress || (await isPersonOn(trip, email))
  ? tripWriteScope(trip.id)
  : undefined;
```

`undefined` is not a refusal. `openSession` reads it as "no narrowing" and mints
`SESSION_SCOPE.agent` — the owner's unqualified `write:content`.

**Reproduction.** Robin is listed in `people:` on `alps-2026` and on nothing
else.

1. `POST /api/auth/request {user, email: robin, kind: "agent", trip: "alps-2026"}` — allowed, code mailed.
2. `POST /api/auth/verify {user, email: robin, code, kind: "agent"}` — note the missing `trip`.
3. The response is `{"scope": ["write:content"]}`.
4. `POST /api/v1/<user>/trips/honeymoon-2026/days` with that token returns `201`.

Naming a trip they are *not* on does the same thing, by the same branch.

**Impact.** Everything gated on `session.scope !== SESSION_SCOPE.agent` opens at
once: read and write every trip in the journal including `private` ones, read
every unpublished draft, publish, create and delete trips, `PATCH .../config`,
and set the journal's own deletion in motion. It does **not** open the contacts
admin surface or the invite endpoints — those ask `isOwner()`, which compares
the session's address against `owner.email`. That is the whole of the bound, and
it is the shape the fix should take.

The attacker is somebody the owner deliberately let onto one trip: a name in
`people:`, or a buddy the owner approved through a link (B33). `lib/tripPeople.ts`
states the property this breaks in its own words — "being on somebody's Vietnam
trip is not a reason to be able to rewrite their honeymoon."

### 2. B231 — a trip-scoped token downloads the whole journal from export.zip

**High.** `app/[user]/export.zip/route.ts:33`.

```ts
const isOwner = auth.ok && ownsUser(auth.session, user);
const archive = createUserExportArchive(user, isOwner ? "all" : "open-to-link");
```

`ownsUser` answers one question — which journal the token belongs to — and it is
deliberately narrow. Every other route granting journal-wide authority pairs it
with `session.scope !== SESSION_SCOPE.agent` or with a per-trip `mayWriteTrip`.
This one has neither, and the local variable's name is what makes it read as
correct.

**Reproduction.** With a legitimately trip-scoped token
(`write:trip:alps-2026`), `GET /<user>/export.zip` returns an archive
containing `trips/honeymoon-2026/trip.md` — a `private` trip the holder was
never on — and `2026-08-25-the-quiet-week.md`, an unpublished draft inside it.

**Impact.** Every `private` and `guest` trip in the journal, every `costs.md`
and `plan.md`, and every unpublished draft, in one request, to the lowest-trust
credential the system issues. Independent of B230 and reachable without it.

`lib/exportZip.ts`'s own docstring says the `"all"` scope is for
`scripts/export.ts` and that "nothing here is exposed over HTTP". That stopped
being true when the route learned to serve it.

`app/api/v1/[user]/drafts/route.ts` has the same first line and is fine — it
pairs `ownsUser` with `writableTrips`, which gates per trip.
`app/api/v1/[user]/config/route.ts` GET has a much smaller version of the same
gap (a trip-scoped token reads the journal's `features` block); it is folded
into B231's Work rather than filed separately.

### 3. B232 — the reactions endpoint answers for a trip nobody may read

**Medium.** `app/api/reactions/route.ts:16` and `:54`.

Both verbs resolve the trip with `getTrip` and never call `mayReadTrip`.

**Reproduction.** Anonymously, with no cookie and no token:

- `GET /api/reactions?trip=<user>/<a private trip>` → `200`.
- `GET /api/reactions?trip=<user>/no-such-trip` → `400 unknown_trip`.

**Impact.** An existence oracle over ids that are guessable by construction —
which is the premise of B117, the ticket that took a closed trip's *title* off
the sign-in gate for exactly this reason. Every write route is careful about
this and says so at length in `lib/api/auth.ts`; this read route is not.

Second, `getAllCounts` is keyed by day slug and a slug is `slugify(title)`, so a
closed trip anybody has reacted to also publishes a lossy copy of its day
titles. And `POST` gates on the same `getTrip`, so a stranger can create those
rows against a trip they may not read — graffiti rather than disclosure, but it
is what makes the slug leak self-serve.

Separately, the route never asks `isEnabled("reactions", username)`: a journal
that switched reactions off still accepts and reports votes here. That is B165's
shape one endpoint over, and it is folded into the same ticket.

### 4. B233 — the https-only rule is not re-applied after a redirect

**Low.** `lib/api/fetchMedia.ts`.

The file's stated first rule is "**https only.** No http, no file:, no gopher:,
no data:." It is enforced once, before the redirect loop. Inside the loop the
next hop is re-resolved and re-pinned — B03's fix, and it holds — but the
scheme and port are never re-asked, and `pinnedRequest` builds from
`url.port || 443` while ignoring `url.protocol`.

**Reproduction.** A `302` to `http://example.com:8080/next.jpg` is followed, and
the second transport call receives a URL with `protocol === "http:"` and
`port === "8080"`. The same URL sent directly is refused.

**Impact.** Not internal SSRF: `checkHost` still runs on the redirect target, so
every private, loopback, link-local, NAT64 and v4-mapped range is still refused,
and `dns.lookup("")` returns nothing so `file:` and `data:` land on the
`nonexistent` branch. What remains is a caller-chosen port on a caller-chosen
*public* host, reached over TLS. Low. Filed mainly because the comment and the
code disagree, and that gap is what the next editor inherits.

### 5. B234 — an unauthenticated health check discloses server paths and journal names

**Low.** `app/api/health/route.ts`, `lib/users.ts:158`. No test — the fault
state needs an unreadable content root, and asserting on it would mostly assert
the harness.

`content: { ok: false, error }` carries the absolute content-root path and the
errno text; `config: { ok: false, error }` carries the same class of detail.
Both are anonymous, and both appear precisely when the instance is already
unhealthy. The `journals` block additionally names any journal that has narrowed
a capability, including one whose own `config.json` says `visibility: private`
— a small hole in a promise that is otherwise carefully kept.

Reconnaissance rather than a way in, hence low. It is also the first thing an
external probe under B101 would read.

## What was looked at and held

Written down because a sweep that only records failures spends the next sweep's
budget re-checking the same ground.

**The two credentials, and `cache()` (B53).** `resolveSession` is memoised on
`(token, expected)`, so `(t, "guest")` and `(t, "agent")` are separate entries
and `row.kind !== expected` runs for each. `cache()` reads a per-request
dispatcher off React's internals and memoises nothing when there is none, so it
cannot outlive a request and cannot survive into a script or a test.
`test/session-cache.test.ts` installs and removes the dispatcher by hand and
asserts the wall in both directions. Held. The wall itself — cookie for read,
bearer for write — is enforced in one place and is not bypassable from any route
I could find.

**Username as a directory name.** `USERNAME_RE` is `^[a-z0-9][a-z0-9-]{1,30}$`,
`ID_RE` is the same shape, `parseTripRef` applies both and refuses a `/` in the
id, and `tripDir` returns a path containing a NUL byte for a ref it cannot parse
rather than a joined one. `resolveMediaFile` rejects empty, `.`, `..` and NUL
per segment and then re-checks that the resolved path is still under the trip's
media root. `ALWAYS_RESERVED` is in code as well as config, so a self-hoster
cannot make `/api` resolve to a person by deleting a line. No traversal
candidate found.

**Frontmatter injection (B204, B178).** `quoteScalar` escapes backslash, quote,
CR/LF, tab and every other C0 control to `\uXXXX`, so it cannot emit invalid
YAML whatever it is handed; `singleLineProblem` refuses a multi-line title at
the door so the caller hears about it rather than getting a 201 for a title
nobody asked for. Both writers share the one quoter. The only unquoted
interpolations left on the write path are `cost.amount`, `lat` and `lng`, and
`validateEntry` requires all three to be finite numbers before `createDraft`
runs — on both doors, REST and MCP. `costsVisibility` is refused rather than
defaulted on write, and reads as `guests` on parse. Held.

**`visibility`, `listed`, drafts and `test:`.** An unrecognised trip visibility
reads as `private` and is logged; an unrecognised invite `kind` reads as
`personal`; an unrecognised `costsVisibility` reads as `guests`; `listed: true`
on a trip nothing advertises is refused at the writer and ignored at the reader.
Every one of these falls to the closed end. `isIndexable` excludes `test` trips
from sitemap, feed and search index. `markdownTwin`, `story.json` and the media
route each apply `mayReadTrip` themselves rather than relying on a layout —
`lib/tripGate.ts` explains why that was necessary, and it is done consistently.
The media route additionally withholds a draft day's photographs from anybody
but the owner.

**Media (B02).** No upload path can produce an SVG: the extension allowlist
excludes it, and anything claiming a permitted extension must decode through
sharp. Originals are stored in a sibling directory no route resolves into, and
the resize cache is under `.cache/` for the same reason. The media route sets
`default-src 'none'; sandbox` on the response itself *as well as* the config
declaring it for the path, so the policy cannot drift from the route tree, and
`Content-Disposition: attachment` is added for `image/svg+xml` specifically. The
baseline CSP has `frame-ancestors 'none'`, `object-src 'none'`, `base-uri
'self'`, `form-action 'self'`; `script-src 'unsafe-inline'` is a documented and
argued trade, not an oversight. `test/security-headers.test.ts` asserts the
media override wins by ordering. Held, and better documented than most of what
this review covered.

**SSRF (B03, B36).** The pin is real: `checkHost` returns the addresses it
inspected and `pinnedLookup` hands exactly those to `https.request`, so there is
no second resolution to differ. Both happy-eyeballs callback shapes are handled.
TLS still verifies against the name via `servername`, and an IP literal
correctly omits it. Addresses are compared as bytes, not strings, and the ranges
are right — `0`, `2130706433`, `0177.0.0.1`, the empty name and `localhost` were
each checked against the real resolver and every one lands where it should.
Redirects are followed by hand, capped at three, each re-checked and re-pinned.
Two separate clocks bound the response and the body, and the size cap is
enforced while reading rather than from `Content-Length`. Only the scheme
re-check is missing (B233).

**Rate limiting (B04, B222).** Both public functions go through one `take()`, so
the sweep runs for every bucket; each bucket carries its own window, so a
namespaced bucket is no longer judged by the default's. The sweep is throttled
to once a second. Correct. `clientIp` trusts the first `X-Forwarded-For` value,
which is only safe because `deploy/Caddyfile` overwrites rather than appends —
that is B01, still open, and the docstring says so plainly rather than
pretending otherwise.

**Journal config (B182).** The ceiling holds: `setJournalFeatures` asks
`resolveCapabilities()` before switching anything *on* and refuses with the
server's own reason; switching off needs no permission. `owner.email` is
genuinely unwritable — the route refuses any key but `features` **by name**
rather than ignoring it, `setJournalFeatures` writes only
`features[name].enabled`, and the rest of the file survives a
parse/merge/write-back that rolls itself back if the result does not read.
Unknown feature names are refused, so `__proto__` and friends never reach an
assignment.

**Confirmations and deletion.** `agentConfirm` is an HMAC over action, scope,
target and issue time, split on exactly three parts (the `_`-in-base64url bug is
fixed), constant-time compared, five-minute window, and deliberately not
single-use with the reasoning recorded. Deletion does not use it: the second
step is a 32-byte token, hashed at rest, hour-lived, single-use, bound to the
username in the URL as well as to its row, mailed to `owner.email`, and consumed
before anything is removed. `.../delete/<token>/export.zip` serves the full
archive on that token and is right to.

**Contacts at rest.** AES-256-GCM, key from the environment only, AAD bound to
`<owner>:<contact id>` so a blob copied into another row fails to decrypt rather
than becoming somebody else's address. Key parsing refuses anything that is not
32 bytes rather than padding. Nothing logs a plaintext, a ciphertext or a key.
The admin surface and the invite endpoints are the only things gated on
`isOwner()` — address, not merely journal — which is the strongest check in the
codebase and is applied exactly where the most sensitive data is.

**Invites.** Neither link grants anything; both end at a pending contact and an
owner's decision. Tokens are hashed at rest. `trip_id` is stored null for any
kind but `buddy`, so a guest link cannot be read as a link to join something.
`approveContact` really is the only thing in the codebase that creates a grant.

**MCP.** Every tool is scoped by the session and never by an argument. Origin is
checked for the DNS-rebinding case, and an absent `Origin` is allowed, which is
correct for the non-browser clients that MCP clients actually are. No token is
passed downstream because there is no downstream. The idempotency store
fingerprints the *arguments*, so a reused key with a different call is a
conflict rather than a wrong replay; it is per-process and in memory, which the
docs state honestly rather than paper over.

**Rendering.** `react-markdown` 10.1.0 with `remark-gfm` and no `rehype-raw`, so
markdown cannot inject an element, and the default `urlTransform` strips
dangerous schemes from links and images. The one `dangerouslySetInnerHTML` is
JSON-LD built from typed fields with `<` escaped. `proxy.ts`'s `gonePage`
escapes the four characters it interpolates. `safeDestination` is a careful
open-redirect check — no scheme, no `//`, no backslash, no control characters,
`..` resolved against a base that exists nowhere, and the result confined to
`/<username>` — and it is applied on the way out as well as on the way in.

**CSRF.** The guest cookie is `httpOnly`, `sameSite: "lax"`, `secure` in
production, and every state-changing route that reads it is a POST, so a
cross-site form does not carry it. Nothing found.

**Login codes.** Six digits with rejection sampling, hashed at rest,
constant-time compared, five attempts then burned, superseded on re-issue, and
rate-limited per address bucket at the route. `verifyCode` answers uniformly for
"no code", "expired", "wrong" and "burned". The standing welcome link is
correctly excluded from `verifyCode`'s lookup and from `revokeCodes`, so it
neither shadows a real code nor dies when one is issued.

## Dismissed

- **`journalMediaBytes` walks the whole journal on every upload.** A cost, not a
  vulnerability, and only when a quota is set.
- **`fetchImage` reaches arbitrary ports on public hosts.** Real, but it is the
  residue of B233 rather than a second finding, and it is written into that
  ticket.
- **`existing = readdirSync(mediaOut).length` counts video posters toward the
  per-day cap.** Off by a few, in the restrictive direction. Not a security bug.
- **`GET /api/v1/<user>/config` has no scope check.** True — a trip-scoped token
  can read the journal's `features` block. Too small for its own ticket; folded
  into B231's Work, where the same mistake is being fixed in the same idiom.
- **The MCP idempotency store is per process.** Documented, and the durable
  safety net (the filesystem refusing to overwrite a day) is unchanged.
- **`agentConfirm` codes are replayable inside five minutes.** Deliberate, with
  the reasoning recorded in `docs/plans/W28-agent-safety-gates.md`. Deletion,
  which is the unrecoverable one, does not use it.
- **`dangerouslyAllowSVG: true` in `images`.** Paired with
  `contentDispositionType: "attachment"` and a `sandbox` CSP on `/_next/image`,
  and content media never goes through the optimiser anyway.
- **`X-Forwarded-For` taken on trust.** Already B01. Not re-filed.
- **`fetchImage` re-resolving the hostname after checking it.** Already B03, and
  fixed. The pin was verified rather than assumed.
- **Rate-limit state per process, in memory.** Already B04.

## What a code review could not reach

- Whether the deployed Caddyfile actually sets
  `header_up X-Forwarded-For {remote_host}`. B01 depends on it, and only the
  running host can answer.
- The real CSP as browsers receive it, after Caddy and any CDN in front.
- TLS configuration, HSTS as actually served, and certificate handling.
- Postgres in production: the tests run SQLite, and `lib/db/` is the only thing
  that knows the difference.
- Timing behaviour under load — the auth endpoints' uniform answers were read,
  not measured.
- Anything about the process's own environment: whether `SESSION_SECRET` and
  `CONTACTS_ENCRYPTION_KEY` are strong, and whether `features.mail.keepCopy` is
  on in production, which would put every code and invite link on disk in
  plaintext.

## Worth probing live under B101

Not this task's to start. In order of what it would cost an attacker:

1. **B231** — one `GET /<user>/export.zip` with a trip-scoped token. The
   cheapest possible confirmation, and the highest payoff.
2. **B230** — request an agent code naming a trip, verify without the field,
   and read the `scope` in the response. Two requests.
3. **B232** — walk a short dictionary of trip ids against `/api/reactions` and
   see which answer `200`. This is the one genuinely easier from outside than
   from the source, because it needs real ids.
4. **B234** — read `/api/health` anonymously and see what the live instance
   actually discloses, including whether `journals` names anything private.
5. **B01**, which is not this sweep's to fix but is trivially testable live:
   send `X-Forwarded-For: 203.0.113.<n>` with a rotating `n` against
   `/api/auth/request` and see whether the limit resets.
